# X-Gate-AI 重构方案说明

## 一、架构调整概述

本次重构采用清晰的分层架构，引入策略模式和模板方法等设计模式，降低模块间耦合。

### 重构前问题
- `ProxyAdapter` 类长达 972 行，职责过多（路由、日志、HTTP、SSE、统计）
- `AdminService` 混合业务逻辑与展示层逻辑
- Mapper 无接口，无法 Mock 测试
- 错误处理分散，缺少统一规范
- 命名不清晰（如 `channel` 既指代模型通道又指代客户端 Key）

### 重构后分层架构
```
┌─────────────────────────────────────────────────────────┐
│                    Controller Layer                      │
│   GatewayController (对外API)    AdminController (管理端)  │
├─────────────────────────────────────────────────────────┤
│                     Service Layer                        │
│   GatewayService (网关核心业务)    AdminService (管理业务)   │
├─────────────────────────────────────────────────────────┤
│                    Strategy Layer                        │
│   UpstreamStrategy (上游路由策略接口)                       │
│   ├── PollingStrategy (轮询策略)                          │
│   └── FallbackStrategy (故障转移策略)                      │
├─────────────────────────────────────────────────────────┤
│                   Component/Adapter Layer                  │
│   ProxyAdapter (HTTP透传适配器)   EncryptUtil (加密工具)    │
│   CallLogService (调用日志服务)    GatewayLogger (日志组件)  │
├─────────────────────────────────────────────────────────┤
│                      Mapper Layer                        │
│   接口定义: UpstreamProviderMapper, ModelChannelMapper     │
│   实现类:   UpstreamProviderMapperImpl                    │
├─────────────────────────────────────────────────────────┤
│                       Entity Layer                       │
│   UpstreamProvider, ModelChannel, CallLog                 │
└─────────────────────────────────────────────────────────┘
```

## 二、设计模式选型

| 模式 | 应用场景 | 改进点 |
|------|----------|--------|
| 策略模式 | 上游路由（轮询/故障转移） | 解耦路由逻辑，支持动态切换策略 |
| 模板方法 | 非流式/流式对话转发 | 提取公共骨架，子类实现差异步骤 |
| 观察者模式 | SSE 流式数据块传递 | 解耦数据接收与写出 |
| 单例模式 | OkHttpClient 实例管理 | 复用连接池，减少资源消耗 |
| 工厂模式 | 响应对象构建 | 统一错误响应格式 |

## 三、模块职责划分

### 3.1 Controller 层
- `GatewayController`: 接收 OpenAI 兼容请求，委托给 GatewayService
- `AdminController`: 管理端 CRUD 操作，委托给 AdminService

### 3.2 Service 层
- `GatewayService`: 核心网关业务逻辑，包含路由决策和调用编排
- `GatewayStrategy`: 上游路由策略接口
  - `PollingStrategy`: 轮询策略实现
  - `FailoverStrategy`: 故障转移策略实现
- `AdminService`: 管理端业务逻辑
- `CallLogService`: 调用日志统计服务

### 3.3 Component 层
- `ProxyAdapter`: HTTP 透传适配器（仅负责出站请求）
- `GatewayLogger`: 网关日志组件（控制台框式日志 + 文件日志）
- `EncryptUtil`: API Key 加解密工具

### 3.4 Mapper 层
- 提取 `IUpstreamProviderDao`、`IModelChannelDao`、`ICallLogDao` 接口
- 实现类通过 MyBatis-Plus 的 BaseMapper 注入

## 四、关键改进点

### 4.1 ProxyAdapter 拆分
原 972 行的巨型类拆分为：
- `GatewayService` (250行): 路由决策和调用编排
- `ProxyAdapter` (300行): HTTP 透传实现
- `GatewayLogger` (200行): 日志组件
- `UpstreamStrategy` 接口: 路由策略定义

### 4.2 命名优化
| 原名 | 新名 | 说明 |
|------|------|------|
| `channel` (变量) | `modelChannel` | 明确指代模型通道 |
| `provider` | `upstreamProvider` | 明确指代上游服务 |
| `resolveCandidates` | `selectUpstreamCandidates` | 更语义化 |
| `rebindModel` | `rebindUpstreamModel` | 明确目标 |

### 4.3 错误处理增强
- 定义 `GatewayException` 异常层次
- 统一错误码规范（OpenAI 兼容）
- 关键操作增加降级逻辑

### 4.4 可测试性提升
- Mapper 提取为接口，便于 Mock
- Service 层依赖注入，可单元测试
- 日志组件独立，可验证输出
